# Review methodology

Review both the diff and its contracts with unchanged code. Trace inputs through real producers, boundaries, and consumers. An approval must rest on verified claims. Apply the configured posting policy: the quality checks below never authorize posting or approving by themselves.

1. **Trace every new signal to its consumer.** For each new field, flag, output, or branch the diff introduces, cite the exact production file:line that consumes it — or conclude that nothing does and treat the feature as inert, which is blocking regardless of test results. Search the whole repo from the repo root with no file-type exclusions: wiring often lives in `.md` prompts, YAML workflows, and JSON schemas rather than code. "It's serialized/returned/printed" is emission, not consumption; an explicit key allow-list or a schema with `additionalProperties: false` between producer and consumer kills a signal silently.

2. **Audit each acceptance criterion for production reachability.** For every stated AC, decision-table row, and "handles X" claim, trace the real production path that exercises it: who produces the inputs, and can they actually take the required shape, cardinality, and ordering? A demonstration on hand-built inputs counts only after you show the production producer can emit those inputs — if your synthetic input mirrors the unit tests' fixtures, that is a red flag to chase, not confirmation.

3. **Close open questions with tool calls, not narrative.** Whenever you catch yourself writing "presumably", "should", "would keep", or "it's reasonable to assume" about reachability, cardinality, consumption, or ordering — stop and read the code or grep instead. Verify uncertain claims directly against the relevant code and runtime evidence.

4. **The PR description is claims, not facts.** Verify test counts, coverage statements, and checked-off ACs yourself. Green tests validate the layer they exercise; name the layer the likely failure mode lives in (usually the integration between the diff and unchanged code, or between the diff and the production runtime) and check whether any test covers that layer. If the tests mock the very component the diff newly depends on (a static utility, an HTTP client, a library entry point), that integration is untested no matter how many tests pass: say so in the Tests section and go find production evidence instead (item 7).

5. **Approval gate.** Before approving, write down the strongest concrete reason this PR should not merge, and refute it with cited evidence: file:line references or command output. If the refutation depends on an assumption you have not verified, do not approve — state the open question plainly and follow the configured posting policy. Asking is the safe harbor; approving on an unverified assumption is the failure mode.

6. **Skeptic pass (targeted, conditional).** Run this before an approval only when the diff matches an archetype it exists to catch: it introduces a new signal, field, flag, or output consumed by another component, it claims acceptance criteria / decision-table behaviors, or it adds a new call into existing code or a library from a path that is hotter or more critical than that code's current callers. For refactors, test-only changes, docs, and straightforward bug fixes, the approval gate above is sufficient — skip the skeptic. When it applies and your agent supports independent subagents, use a fresh context for each of the 2-3 highest-risk claims from the draft review. Use the backend's available delegation tools and a suitable model; do not assume a particular tool name or model alias. If delegation is unavailable, perform a separate skeptical pass yourself and state that limitation. Do NOT ask them to re-review the PR. Give each one the worktree path, its single claim with the file:line evidence you cited, and the reproduction rule (item 9) verbatim, and instruct it to attack that claim by running, not reading: build and run the smallest reproduction that exercises the real producer and the real consumer on both sides of the boundary with production-shaped inputs, and return the exact script, the command, and its trimmed output as the finding — either the claim holds under execution, or here is the run that breaks it. Only when the behavior is not executable in the worktree may it fall back to reading, and it must say so and why. Always add these two questions, independent of your draft, so the skeptic does not inherit your frame: which code or library does this diff exercise for the first time on this path in production, and is there evidence it works there today; and what is lost downstream if the new code throws anything at all or hangs? Address every issue it raises with cited evidence. Anything you cannot refute becomes an open question in your review, and the approval gate remains unmet; follow the configured posting policy.

7. **Runtime evidence for new call paths.** When the diff puts existing code or a library on a new path — a hotter one, a more critical one, or one that runs under a different classloader, thread pool, or credential than its current callers — static reading and unit tests cannot tell you whether it works there. Query production logs for the callee's error signatures before approving. The search target is the **callee chain**: walk from the diff's new call site down to the library entry point it reaches (for example `getPRStatus` → `getPullRequest` → `buildGitHubClient` → `GitHubBuilder.build()` → `GitHubClient.<clinit>`) and search for those class and method names in stack traces over the last 7 days — not for the types the diff happens to import. Use only logs and services the user has authorized you to access. If runtime access is unavailable, identify the verification gap; do not assume internal tools or credentials exist. A zero result is not evidence until you have validated the scope: first run a query that must return hits in the same index and window (the component's own WARNING prefix, or any log line you know it emits); if that returns zero too, the scope is wrong, fix it and rerun. Any existing `Error` or class-initialization failure in the same library or client the diff newly calls is directly relevant no matter which current caller triggers it, and is a blocker for any change that makes more depend on it. Record the validated query and its result in the review so the next reviewer can rerun it.

8. **Exceptions are not Throwables; name the blast radius.** For each new call on an existing critical path, state what it can throw — including `Error` and `LinkageError` from class initialization, which `catch (Exception)` does not catch — and what is lost downstream if it escapes or hangs. "The callee cannot throw" is an unverified claim unless the guard covers `Throwable` and you have read the callee's dependencies. If the answer to "what is lost" is an existing event, emit, dispatch, or trigger, that is Major, not a nit about a redundant catch: best-effort enrichment must never sit upstream of the thing it enriches unless the guard is `Throwable`-wide and tested with an `Error`.

## Review structure

9. **Reproduce before you assert; run what you can.** Reading tells you what the code says; only running tells you what it does. For every Blocker and Major you intend to post, and for every high-risk Spec claim (a new signal reaching its consumer, an AC's production path, a contract with unchanged code), decide whether the behavior is executable inside this worktree: a function you can call from a throwaway script, a CLI you can invoke, a parser or schema you can feed the production-shaped input, a service you can start on a local port, a test you can write across the actual producer→consumer boundary. When it is, build the smallest reproduction that exercises the real code on both sides of that boundary — not a re-run of the PR's own unit tests, which already pass, and not a mock of the very component in question — run it, and cite the exact command and trimmed output in the finding, in a collapsed <details> block so the author can rerun it. The reproduction lives outside the tree (mktemp) or in a scratch file you delete afterwards; never commit it. A claim that could have been run and was not is an unverified assumption for the approval gate in item 5. When the behavior is not executable here (it needs a Jenkins controller, a cluster, external credentials, or a classloader or runtime you do not have), say so in the finding, name what evidence stood in for execution (production logs per item 7, a rendered manifest, a static trace), and raise the fidelity gap as an open question only when it is the layer where the likely failure lives. A reproduction that does not reproduce a suspected bug is a result, not a failure: report it, lower the finding's severity or drop it, and never withhold approval merely because a reproduction could not be built.

Structure every posted review as: **Verdict** / **Spec** (AC-by-AC, each with the production-path evidence that it is met and reachable) / **Blockers** / **Major** / **Minor** / **Tests** (what the suite actually exercises, and which layer it does not) / **Reproductions** (every reproduction you or the skeptics ran, each as a collapsed <details> block with the command and trimmed output, and what it confirmed or refuted) / **Verification** / **Questions**. Omit sections that are empty, except **Verification** when the diff changes telemetry, events, or anything observable after rollout: list the exact queries (Splunk SPL, log greps, API calls) that prove the new behavior landed and that its failure signature did not appear, so whoever rolls it out has a checklist instead of a memory.
